# DeliveryKit.LogArchiver

DeliveryKit.LogArchiver は、180日経過したログを安全に隔離するバッチ処理です。

## Features

- ログ削除ではなく「隔離」（削除は `purgeDays` を指定したときだけ。既定は削除しない）
- File.Move のみを使用（安全）
- カテゴリ別ディレクトリに対応（名前は決め打ちせず、その場にあるものを対象にする）

## How It Works

1. ログフォルダの直下にあるディレクトリ（カテゴリ）を全て走査
   （監査で発覚：以前は6つの名前を決め打ちしており、`DeliveryLogger` に
   独自のカテゴリ名を渡していると**そのログだけ隔離も削除もされなかった**）
2. 最終更新日が 180 日前のログを検出
3. LogsArchive フォルダへ移動
4. `purgeDays` が指定されていれば、LogsArchive 内の期限切れログを削除

## Usage

```
DeliveryKit.LogArchiver.exe [basePath] [archivePath] [days] [purgeDays]
```

引数は省略可能。省略時は実行ディレクトリ配下の `Logs` / `LogsArchive`、保持期間180日を使う。
環境変数 `DELIVERYKIT_LOG_PATH` / `DELIVERYKIT_LOG_ARCHIVE_PATH` / `DELIVERYKIT_LOG_PURGE_DAYS`
でも上書きできる。特定ドライブ・特定ユーザー構成の絶対パスをコード側にハードコードしないこと。

Windows タスクスケジューラで 1 日 1 回実行することを推奨します。

## 隔離したログの削除（`purgeDays`）

**このツールを動かしているだけでは、ログは一切減りません。** `days` 日を過ぎたログを
`LogsArchive` へ移すところまでが従来の動作で、移した先を片付ける仕組みがありませんでした
（監査で発覚）。毎日動かすほど `LogsArchive` だけが増え続け、次の2つが起きます。

- **ディスクが埋まる。** Azure App Service のようにローカルディスクが小さい実行環境では、
  ログの置き場が満杯になった時点でアプリ自体が書き込みに失敗します。
- **ログに含まれる個人データが、利用者に約束した保存期間を越えて残る。**
  「隔離済み」は「削除済み」ではありません。約束した期間で消していると思い込んだまま
  運用できてしまうのが、いちばん困る点です。

`purgeDays` を指定すると、`LogsArchive` 内の最終更新から `purgeDays` 日を過ぎたログを
削除します。**既定は 0（削除しない）** で、指定しない限り従来どおりの動作です
（更新した途端に黙ってログが消えることを避けるため）。

```
DeliveryKit.LogArchiver.exe Logs LogsArchive 30 90
```

- 30日で `LogsArchive` へ隔離し、90日で削除する。
- `purgeDays` が `days` より短い設定は、隔離される前に消えることになるため無効として扱い、
  削除を行いません（標準エラー出力に理由を出します）。
- 保存期間は事業者が利用者に示している期間と揃えてください。コード側の既定値は
  「消さない」であり、**期間を決めるのは配布先の責任**です。

## 制約（監査で発覚、docs追記）

- **このツールは実行された分しか働きません。** Windows タスクスケジューラでの運用を
  想定した単発の実行ファイルのため、Linux コンテナや Azure App Service（Linux）のように
  スケジューラを前提にできない実行環境では、**誰も起動しないまま無期限にログが溜まります。**
  そうした環境では、ホスト側のcron相当の仕組みを別途用意するか、アプリのプロセス内で
  定期実行する常駐処理として同等の処理を組み込んでください
  （DeliveryKit 本体は後者を採り、API のプロセス内で1日1回動かしています）。
