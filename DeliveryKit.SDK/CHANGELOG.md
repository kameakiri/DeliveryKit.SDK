## 0.3.0

**この版は 0.2.0 から利用者のコードに影響する変更を含みます。**
以下は 0.2.0 の公開以降に入れた変更で、**これまでCHANGELOGへの記載が漏れていました**
（監査で発覚。10件ほど遅れており、そのうち2件は利用者のコードを壊す変更でした。
変更履歴は「上げてよいか」を判断するためのものなので、載っていないと判断できません）。

### 破壊的変更

- **`CreateDeliveryRequest.IdempotencyKey` を必須にしました。**
  未指定のリクエストは400になります。クライアント側で1操作につき1つGuidを生成し、
  再送時は同じ値を送ってください。サーバー側でGuidを作っても、リクエストごとに別の値に
  なるため再送を同じ操作だと判別できません。
- **`DeliveryKit.ApiTemplate` の名前空間を `DeliveryKit.Api.*` から
  `DeliveryKit.ApiTemplate.*` へ変更しました。** 本家APIと同じ名前空間だと、
  両方を参照したときに型が衝突します。テンプレートをコピーして使う場合は
  自分の名前空間へ置き換えてください。

### DeliveryKit.ApiTemplate

- `/health` を追加（`GET` と `HEAD` の両方、認証不要）。稼働監視・ロードバランサの
  ヘルスプローブ用。**`AllowAnonymous` を外すと監視から401になり「常に停止中」と見えます。**
  DBには接続しません（DBの一時的な不調でオリジンごと切り離されるのを避けるため）。
- 本文のバインドに失敗したときの応答を `{ error, field }` に統一。
  既定の ProblemDetails はフレームワークの英語メッセージで、画面にそのまま出せません。
- 未認証で受け付けるPOSTに `[RequestSizeLimit]` を追加。指定しないとKestrelの既定
  （30MB）まで本文を受け取ってモデルバインドが解析します。
- 書き込み系エンドポイントとログインにレート制限、ログイン監査ログを追加。
- JWT検証の `ClockSkew` を明示。
- 冪等性の指針をREADMEに追加。
- 全応答に `Cache-Control: no-store, private` を付けました。APIが返すのはほぼ全て
  テナントの業務データ（氏名・住所・電話番号・金額）で、キャッシュ制御を指定しない
  200応答はブラウザのヒューリスティックなキャッシュの対象になり、共有端末の
  ディスクに残り得ます。本家8モジュールは同じ理由で一律に付けており、
  このテンプレートだけ漏れていました。
- **書き込み系（`create`）のレート制限を、送信元IP単位から利用者単位へ変更しました。**
  IPで分けると、同じ事務所からの操作はNATの外側から見ると全員が同じ送信元IPになるため、
  5人で入力すれば1人あたり4回/分で上限に達します。サーバ間の呼び出しも
  少数の固定IPへ集約され、利用者が何人いても合計で頭打ちになります。
  本家8モジュールは同じ理由で先に直しており、**その土台であるこのテンプレートだけが
  取り残されていました。** あわせて `UseRateLimiter()` を `UseAuthentication()` の
  後ろへ移しています（この順序でないと `HttpContext.User` が空で、利用者単位に
  分けたつもりが全員IP単位のままになります）。

### DeliveryKit.SDK

- README / `docs/getting-started.md` のサンプルが、ログへ個人情報を書く形になっていたのを是正。
- `docs/core.md` のサンプルを `IdempotencyKey` 必須化に追従。
- `DeliveryKit.LogArchiver` の `Nullable` / `ImplicitUsings` を他プロジェクトと統一。
- **`DeliveryKit.LogArchiver` に隔離先のログを削除する `purgeDays` を追加しました**
  （第4引数、または環境変数 `DELIVERYKIT_LOG_PURGE_DAYS`）。
  **既定は 0（削除しない）で、これまでの動きは変わりません。**
  従来は「削除ではなく隔離」を売りにしながら**隔離した先を片付ける仕組みが無く**、
  毎日動かすほど `LogsArchive` だけが増え続ける状態でした。困るのは容量よりも
  保存期間の方で、このSDKで作った製品の事業者が利用者へ保存期間を示していても、
  ログに含まれる個人データはその期間を越えて残り続けます。しかも運用者からは
  毎日アーカイバが正常終了して見えるため、約束どおり消えていると思い込んだまま
  運用できてしまいます。**保存期間を決めるのは配布先の責任**なので、
  明示的に指定したときだけ削除します（`docs/archiver.md` 参照）。
- `docs/archiver.md` に「このツールは実行された分しか働かない」ことを明記しました。
  Windowsタスクスケジューラを前提にできないLinuxコンテナやApp Service（Linux）では、
  誰も起動しないままログが無期限に溜まります。
- READMEがUTF-16で保存されGitHubで文字化けしていたのを修正。
- **`docs/ai.md` を実装に合わせて書き直しました。** 「AI 学習用のクリーンデータ生成」
  「LLM 学習用のログ整形」「ノイズ除去」「時系列データの維持」を Features / Purpose として
  挙げていましたが、`Normalize()` がしているのは**空行の除去と前後の空白の Trim だけ**で、
  そのどれも行っていません。あわせて、**マスキングを一切行わない**こと
  （ログには氏名・住所・IPアドレス等が入る）を明記しました。外部のAIサービスへ
  渡す前に確認が必要です。名前空間・プロジェクト名（`DeliveryKit.AI.Pipeline`）は
  変更していません（利用側のコードを壊すため。改名する場合は別の版で）。
- `docs/faq.md` の「ログは削除されますか？」を書き直しました。「削除されません。
  180日後に LogsArchive へ移動されます」とだけ答えており、**移動した先が
  片付かないことが利用者に伝わらない**書き方でした。保存期間を決めるのは
  配布先の責任であることと、`purgeDays` の存在を明記しています。
  「アーカイバを動かしていればログは片付きますか？」も追加しました
  （単発の実行ファイルなので、スケジューラが無い環境では誰も起動しません）。
- `docs/architecture.md` のコンポーネント表と設計方針を実態に合わせました。
  「AI 活用を前提としたログ構造」は、AI向けに何かしている訳ではありません。
- `docs/logging.md` のカテゴリの説明を直しました。5つのカテゴリが固定で用意されて
  いるように読めましたが、実際は `DeliveryLogger` に渡した文字列がそのまま
  ディレクトリ名になります。
- **`DeliveryKit.LogArchiver` が、ログフォルダ直下の全カテゴリを対象にするように
  なりました。** 以前は `core` / `api` / `error` / `security` / `audit` / `access` の
  6つを決め打ちで走査しており、`DeliveryLogger` に独自のカテゴリ名を渡していると
  **そのログだけ隔離も削除もされないまま無期限に溜まり続けました。**
  しかも動かしている側からは、アーカイバが毎回正常終了して見えます。
  隔離先の削除も同様に、隔離先の直下にあるものを対象にします。
- `docs/getting-started.md` の curl 例に、示している資格情報が開発用の既定値で
  あることを明記しました（開発環境以外では未設定のまま起動すると例外で止まります）。
